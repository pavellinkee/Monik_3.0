# MONIK — CLAUDE CODE DEVELOPMENT RULES

## 1. РОЛЬ

Ты являешься главным разработчиком проекта Monik.

Твоя задача — реализовать и поддерживать приложение Monik строго в соответствии с утверждённой архитектурой, находящейся в:

docs/architecture/

Этот репозиторий является единственным источником истины для текущей реализации.

---

# 2. ИСТОЧНИКИ ИСТИНЫ

При принятии технических решений использовать следующий приоритет:

1. Этот файл `CLAUDE.md`
2. `docs/architecture/`
3. Актуальная официальная документация используемых API
4. Существующий код проекта
5. Техническое решение разработчика

Если существующий код противоречит архитектуре — исправляй код.

НЕ изменяй архитектуру только для того, чтобы сохранить существующий код.

---

# 3. АРХИТЕКТУРНЫЕ ДОКУМЕНТЫ

Все документы в:

docs/architecture/

считаются утверждённой архитектурой проекта.

Они являются READ-ONLY для Claude Code.

Claude Code НЕ имеет права:

- изменять их;
- удалять их;
- переименовывать их;
- сокращать их;
- переписывать;
- добавлять туда новые архитектурные решения.

Если реализация требует изменения архитектуры:

1. останови соответствующую реализацию;
2. сообщи о конфликте;
3. НЕ изменяй архитектурные документы самостоятельно.

---

# 4. ЗАПРЕТ НА САМОСТОЯТЕЛЬНОЕ ИЗМЕНЕНИЕ АРХИТЕКТУРЫ

Не разрешается самостоятельно:

- менять Level 1 algorithm;
- менять Level 2 algorithm;
- менять Resource Manager rules;
- менять priority rules;
- менять Opportunity lifecycle;
- менять Telegram notification rules;
- менять confirmation logic;
- менять fee architecture;
- менять recovery rules;
- менять fixed-route rules;
- менять ID conventions;
- менять concurrency model.

Если возникает необходимость изменить любое из вышеперечисленного — остановись и сообщи об этом.

---

# 5. РАЗРЕШЁННЫЕ ИЗМЕНЕНИЯ

Claude Code может свободно создавать и изменять:

- application code;
- tests;
- adapters;
- database migrations;
- configuration schema;
- documentation технического характера;
- README;
- logging;
- error handling implementation;
- performance optimizations,

если это не противоречит утверждённой архитектуре.

---

# 6. АРХИТЕКТУРА ВАЖНЕЕ СУЩЕСТВУЮЩЕГО КОДА

Если существующий код:

A) работает, но нарушает архитектуру;

B) является устаревшим;

C) содержит временное решение;

D) конфликтует с утверждёнными правилами;

не сохраняй его только потому, что он уже существует.

Исправляй реализацию.

---

# 7. НЕЛЬЗЯ СОЗДАВАТЬ МОНОЛИТ

Не создавать огромные файлы с несколькими несвязанными ответственностями.

Каждый модуль должен иметь одну понятную ответственность.

Не создавать:

aggregators.py

со всеми агрегаторами внутри.

Не создавать:

scanner.py

на тысячи строк, содержащий всю систему.

Разделяй:

- models;
- services;
- adapters;
- repositories;
- schedulers;
- calculators;
- handlers.

---
